## 功能讨论时必须保留的约束

1. **单项操作是当前边界。** `POST /tasks/complete` 和 `POST /tasks/postpone` 都只接受一个 `task_id`。bulk completion 仅是未来计划，目标上限 100 项并返回逐项失败；它没有当前实现证据，部署记录也明确说 bulk API 未验证。
2. **团队隔离依赖服务层归属检查。** 当前服务代码以 `team_id` 校验任务；任务不存在或属于其他团队时都返回 404，以避免泄露其他团队任务的存在。讨论批量接口或新读取路径时，需要保持这一不泄露语义。
3. **归档任务不能延期。** 当前 postpone 对 archived 任务返回 409；任何可配置延期方案都需保留或明确修改该规则。
4. **延期默认值目前是 24 小时。** 产品文档与当前服务源码一致。`docs/new-work.md` 中的可配置延期只是未批准提案，不能当成现有需求或已承诺功能。
5. **任务修改与 outbox 入队要求同一事务。** README 和服务代码都体现这一约束，但缺少数据库适配实现及执行证据。讨论批量完成时还需要明确是整批原子提交，还是每项独立提交并报告失败；现有资料没有决定。
6. **通知按 UTC 静默时段处理。** 当前 worker 源码把 22:00 至次日 07:00 UTC 设为静默期，并在静默期返回延迟标记。现有记录称周末提醒是最大投诉，但没有证据解释投诉是否由时区、周末策略、调度或投递失败造成，不能直接归因。
7. **重试上限的表述需精确。** README 写“失败消息最多重试两次”；代码依据 `attempt < 2` 决定 retry，并在 `attempt == 2` 时 dead letter。由于 attempt 的起始值和递增位置不在现有 worker 文件中，完整尝试次数及其与文档措辞是否一致仍未知。
8. **多团队、邀请和审计保留尚未决定。** 当前产品是单团队试点；多团队与邀请仍是开放设计问题，审计保留期也未确定，不能在功能方案中假设已有支持。
9. **线上真实性仍缺生产证据。** 没有生产日志、数据库查询、消息传输记录、错误率、任务样本或用户验收材料。任何关于“生产正常”“提醒已送达”“事务已保证”或“投诉已解决”的说法都超出现有证据。
