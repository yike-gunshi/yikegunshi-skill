# 判活、收结果、验收、返工、收回

## 判活表（`D status` 的 state）

| state | 含义 | 怎么办 |
|---|---|---|
| `STARTING` | 进程活着、还没有事件、启动不到 90 秒 | 等 |
| `STALL_START` | 启动超过 90 秒仍零事件 | 已知的启动卡死症状（历史上一晚两次，重拉即好）。`cancel` 后原样重派一次；第二次还卡就跑 `D doctor` 查环境 |
| `RUNNING` | 有事件在流 | 等 |
| `IDLE` | 有过事件，但超过 10 分钟没有新事件 | 不要直接杀。先看 `log.jsonl` 最后一个事件：卡在一条 `command_execution` 上，多半是测试或服务在等（看命令本身）；停在推理上，高档位静默长尾可能长达 30 分钟。再看 `stderr.log` 有没有网络错误。确认是真挂住（例如网络断了、命令在等交互输入）才 cancel |
| `DONE` | 退出码 0 且出现过 `turn.completed` | 进入收结果 |
| `FAILED` | 退出码非零 / `turn.failed` / 进程被外部杀 | 读 `stderr.log` 末尾。认证或网络错误跑 `D doctor`；任务本身出错就看最终回复，修任务书后重派 |
| `CANCELLED` | 被 cancel 了 | — |

`log.jsonl` 里 `item.type` 为 `error` 的条目可能只是警告（例如 "Under-development features enabled"），stderr 里的 `failed to load skill` 是噪声，二者都不代表失败。

## DONE 不等于干了活

`D result` 出现 `WARNING: EMPTY_DIFF`（非只读作业却没改动）时，可能是三种情况，处理完全不同：

1. **沙箱拦了写入**：同时有 `SANDBOX_BLOCK`，或 stderr 里有 `Operation not permitted`。常见于要写仓库外的路径（`~/.cache`、全局 node_modules）。修法是调整任务（改到仓库内，或由 Claude 预先准备好依赖），而不是让它「再试一次」。
2. **Codex 认为已经做完**：最终回复里说「已经满足」「无需修改」。去核实：真满足就记为通过、无需提交；没满足就是任务书写得不够清楚，返工意见里要点出它判断错在哪里。
3. **它只给了方案没动手**：最终回复里是一段建议。返工意见明确写「直接修改文件」。

## 验收怎么做

1. 重读任务书，逐条看验收标准。问的是「这份 diff 满足这条标准吗」，而不是「这份 diff 自洽吗」。
2. 读完整 diff，包括新增文件。重点看：是否超出「范围」、是否删了或放宽了测试、是否碰了明确不能碰的文件、有没有调试残留。
3. 亲自跑门禁，不要只信 Codex 回复里的「全过」。
4. 前端改动看真实页面（截图或 forge-qa），不靠读 CSS 判断效果。

## 返工意见怎么写

发回原会话，所以不用重复背景，只写差在哪：

```markdown
# 返工 <label> 第 <n> 轮

验收没过的地方：
1. <标准 2>：<观察到的事实，例如第 11 次请求返回 200，期望 429。复现：`curl ...`>
2. <超出范围>：<改了 xxx.py，这个文件不在范围内，请还原>

保持不变：<已经验收通过、这一轮不要动的部分>

改完跑 <门禁命令>，同样不要 commit。最后一条消息只写改了哪些文件和门禁结果。
```

一条意见对应一个可复现的事实。「再优化一下」「还是不对」这种意见会让它乱改一通。

## 什么时候收回

- 同一任务返工两轮仍不过。
- Codex 明确说需要产品或设计判断（这种活本来就不该派）。
- 返工意见写不出可复现的事实，说明问题出在任务书或拆分上，收回后由 Claude 想清楚。

收回不是失败，要记进派活小结的「异常」一栏：哪类任务、卡在哪里。这是下次拆任务时判断「这类活该不该派」的依据。
