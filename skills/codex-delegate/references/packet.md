# 任务书模板

Codex 在知道「为什么」时干得最好；约束只写真正的阻塞项，指定结果而不是指定命令。过度规定会把一个本来能自己找到好路径的模型绑死。

## 模板

```markdown
# 任务 <label>：<一句话任务>

## 背景
我在做 <更大的目标，例如 v32 AI 搜索 MVP>，给 <谁用>。这一步完成后 <它能让什么成立>。
相关文档：<ENGINEERING.md §x / DESIGN.md 模块 y / BF 报告路径>（读它们，不要只看这份任务书）。

## 任务
<一句话。多件事就拆成多份任务书，别捆在一起。>

## 验收标准
1. <可二值判断的结果，例如：`pytest tests/test_ai_search_quota.py` 全过，且新增用例覆盖 24 小时 10 次上限>
2. <行为层面的判据，例如：第 11 次请求返回 429，响应体含 reset_at>
3. <不能靠删测试、放宽断言来通过>

## 范围
- 只改：<目录或文件>
- 不改：<明确不能碰的，例如迁移文件、prompt 文件、其他功能模块>

## 检查点
只在真正需要输入时停下：破坏性或不可逆操作、实质性范围变化、只有我能提供的信息。其他情况一路做完再汇报。

## 收尾
- 跑完验收标准里的门禁就停，**不要 git commit**（沙箱提交不了，由我验收后提交）。
- 不要推送、部署，不要改 `.env`，不要连生产数据库。
- 不要附带可选的解说。最后一条消息只写：改了哪些文件（一行一个）、门禁命令和结果、最多 3 行你认为我验收时该特别看的地方。
```

## 写的时候想清楚

- **验收标准是任务书的核心**。它决定第 5 步怎么验，也决定 Codex 怎么判断自己做完了。写成「代码整洁」「体验好」这种没法判断的，等于没写。
- **相关文档给路径，不要大段复制**。Codex 能读仓库，复制进来的内容会和仓库里的真源漂移。
- **项目特有的硬约束要点名**。例如 info2action 的「池化连接禁止裸 SET」，Codex 不一定读过项目 CLAUDE.md 的那一节，碰到数据库代码就写进「范围」。
- **前端任务**写清楚以哪份设计为准（DESIGN.md 模块号或 token），并说明 Claude 会截图验收。
- **返工意见**是另一种格式，见 `acceptance.md`，不要用这份模板。
