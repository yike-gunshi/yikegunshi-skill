# 设计说明

> 对应 prompt：`prompt.md`（版本 `review_classifier_v1_0_2026_10_22`）。每个模块一句关键决策，后面跟理由。

## 模块 1 · 背景与目标

- **职责边界只留"归类 + 抽问题"**：提醒先后、统计、回复买家、判断买家对不对都不归模型。这几件要么能用代码做，要么归客服。
- **代价倒向写死为"拿不准按差评"**：需求方明确说漏掉真实差评比误判中评更伤，所以每个两可场景（中评、反话、轻微不满）都按这个方向裁决。
- **成功标准写成程序能核对的状态**：每处不满都有一条问题、每条问题带原文逐字片段、归类与问题清单一致。后两条代码可以直接验。

## 模块 2 · 角色与读者

- **类别按"谁要处理"定义，不按情感极性**：判断锚是"客服需要知道这条吗？不需要的话，有没有值得产品看的改进点？"。所以"好评里夹建议"归建议，"已解决的问题"仍归差评。这样结果直接对上下游的两个动作：推给客服、汇总给产品。
- **加了一句防迎合**：prompt 以店家口吻写（"我们网店"），模型容易往好评靠，所以写明"店里要的是真实的不满，不是好看的好评率"。

## 模块 3 · 任务与步骤

- **六步流水线，淘汰在前**：先圈出不算证据的文字（注入、商家话术、商家回复、平台自动文字），再过无效门槛，然后才拆件判定。初稿里信任边界排在拆件之后，注入文字可能先被当成"一件事"拆进去，审查时调到了最前。
- **先分析后输出**：分析区六项固定顺序，最后一项是自查。自查要求说出确认的内容，重点盯长评后半段、"追评："之后和"但是/就是"之后。

## 模块 4 · 标准具体化

- **不用打分量表，用分界检验句**：这个任务没有程度档位，决定去留的是三条线：
  1. 不满与建议：看建议针对的那件事，评论人有没有说过它已经让他不满意；
  2. 中评与不满：只有"还行/一般"这类词才算不表态，带上任何落差就算不满；
  3. 问题类别之间：从上往下取第一个符合的，写明的例外优先。
- **归类是固定优先顺序**：有不满即差评，其次建议，再次好评。规则是机械的，代码可以从问题清单复算，用来校验模型输出。
- **安全类用封闭清单**：只认列出的字眼（漏电、冒烟、焦糊味、接触食物的涂层掉渣等），不让模型自己推断"可能有风险"。这样不会把所有故障都抬成安全问题，代价是清单外的隐患会落到故障或做工类（见遗留风险）。

## 模块 5 · 样例

- **六个完整走查 + 一组出局形态 + 一组速判钉例**：完整走查覆盖差评（夸骂混合、反话加安全、长吐槽）、好评、建议和注入纠偏；出局形态示范广告、平台自动文字、不表态三种"其他"的输出长什么样。钉例专门压两可场景：中评、"有点贵但是值"、"呵呵，真不错"、已解决的问题、转述别人的说法、商家索要好评。
- **每例带推理，不只给结论**：重点演示排除相邻判定的写法，例如"不是 performance，因为……"。
- **全部自造**：没有真实标注集，样例句子以后也不能进验证集（防泄漏）。

## 模块 6 · 边界与兜底

- **不强迫三选一**：在三类之外加了"其他"出口，并要求写明原因（空、表情不明、不表态、广告、无关）。程序统计时可以单独排除这些评论。
- **两种不确定出口**：`ambiguous_tone`（两可或疑似反话，已按代价倒向判定）和 `partial_text`（截断、乱码）。没有用模型自报的置信度：它只能当软信号，枚举更好路由到人工抽检。
- **只有骂、没说哪里不好的评论也进差评**：问题写"仅表达不满，未说明具体问题"。客服可以去问买家，这比丢进"其他"更符合代价倒向。

## 模块 7 · 输入与信任边界

- **只传商品名和评论原文，一次一条**：星级不进 prompt，交给代码去和文字结论对照，低星却没判差评的进抽检；一次一条，避免多条之间互相影响和位置效应。
- **四类非证据文字列表处理**，注入正向路由：要求改变判断的话不作证据，其余内容照常判，去掉后什么都不剩就归广告类。不为攻击另开分支。
- **划清话术和抱怨**：商家话术本身不算证据，但评论人抱怨商家索要好评、返现不兑现，是真实不满，照常记。这条边界是审查时补上的。

## 模块 8 · 输出契约

- **唯一解析点**：程序只取最后一个 json 代码块；分析区只用文字，评论里带 JSON 时用文字描述不照抄。初稿缺"分析区不写代码块"，注入文本自带 JSON 时有干扰风险，审查时补上。
- **字段集中一张表**，枚举全列：`category`、`other_reason`、`issues[]`（type / aspect / problem / evidence）、`uncertainty`。
- **evidence 要求逐字片段**：程序可以直接检查它是否出现在原文里，这是最便宜的"编造问题"探针。

## 模块 9 · Prompt 之外（交给代码和流程）

能用代码做的都不写进 prompt，具体清单见 `遗留风险与验证建议.md` 的"代码侧要做的事"：

- JSON 与枚举校验、归类复算、evidence 子串校验；
- 安全类优先提醒、星级与文字对照；
- 定界标签转义、商家回复在进 prompt 前剥离。
