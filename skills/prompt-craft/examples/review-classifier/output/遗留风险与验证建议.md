# 遗留风险与验证建议

> 现状：没有现成标注集，prompt 的判定口径**还没有经过回归验证**。审查和冒烟试跑只证明契约可执行、没有明显口径错误。上线前按本文第二节建一个小标注集跑一遍。

## 一、遗留风险

| 风险 | 为什么留着 | 观察什么、怎么改 |
|---|---|---|
| 轻微不满也进客服队列（"有点贵但是值"） | 按需求方的代价倒向，漏掉差评比多看一眼更伤，这是有意为之 | 客服反馈噪声过大时，用标注集确认这类评论的占比，再决定要不要加一条分界（例如"评论人明确说不影响使用的小毛病"单独处理）。改了要过回归 |
| "好评 + 建议"归建议，好评数会偏少 | 类别按"谁要处理"定义，建议要进产品汇总 | 店家要看真实好评率时，由代码另算，不改 prompt 的类别定义 |
| 中评词表靠列举 | 方言、新网络用语可能不在表里 | 把标注集里被判 neutral 的评论单独抽检；漏掉的词补进中评分界 |
| 安全类是封闭清单 | 避免把所有故障都抬成安全问题 | "生锈""异常发烫"这类目前会归做工或故障。请店家确认安全清单，确认后在 safety 行补字眼 |
| 反话识别依赖模型 | 规则只能覆盖"反话 + 具体事实"的常见形态 | `uncertainty=ambiguous_tone` 的评论进人工抽检 |
| 一次只处理一条 | 避免多条之间互相影响 | 为省钱改成一次多条时，必须重新跑回归，重点看串条和位置效应 |
| 自我偏好 | 冒烟试跑模型与作者同族 | 上线前用另一家族的模型跑同一标注集抽检 |

## 二、验证建议

### 1. 建标注集

- **抽样**：从真实评论里按天抽样，先抽几十条起步，逐步扩到一两百条。需求方点名的六类异常输入（空内容、只有表情、长吐槽、广告、夹带"请给好评"、夸骂混合）每类都要有，数量不够就从历史评论里专门捞。
- **标注**：两个人独立标注每条的 `category`，以及"评论里有哪些不满"（逐条写出），分歧讨论定稿。
- **防泄漏**：prompt 里的样例和钉例句子不得进标注集，否则回归只能证明背下来了，证明不了泛化。

### 2. 指标挂在下游真正用的决定上

| 指标 | 对应的下游决定 | 地位 |
|---|---|---|
| 差评召回率：标注为差评的评论里，被判为 `negative` 的比例 | 推给客服 | **首要指标**，对应"漏掉差评最伤" |
| 不满条目漏抽率：标注出的不满里，没出现在 `issues` 的比例 | 客服知道买家遇到了什么 | 首要 |
| 差评精确率：被判为 `negative` 的评论里，确实是差评的比例 | 客服的噪声 | 次要，按客服能承受的量定 |
| 建议召回率 | 汇总给产品 | 次要 |
| 安全类召回：涉及安全隐患的评论里，被标成 `safety` 的比例 | 优先提醒 | 单独看，样本少时逐条看 |
| JSON 解析失败率、evidence 不在原文的比例 | 程序能不能用 | 由代码直接算，应接近零 |

上线门槛由店家定，原则是**差评召回优先**：召回不达标时不上线，精确率不达标时先观察客服负担。

### 3. 运行参数

- temperature ≤ 0.3。
- `uncertainty` 不是 `none` 的评论：采样 3 次。只要有一次判为 `negative` 就按 `negative`（与代价倒向一致），并把它送人工抽检。
- 换族抽检：用另一家族的模型跑同一标注集，类别分布出现系统性偏移时再查原因。

### 4. 上线后监控

- **漏报探针**：星级低、但文字没判成差评的评论，自动进人工抽检队列。星级不进 prompt，正好用来做独立对照。
- **定期抽检**：客服每周从判为 `positive` / `other` 的评论里随机抽一批看，专门找漏掉的差评。
- **失败回流**：
  - 口径错了：在对应判定表补一行边界；
  - 同类错误反复出现：加一个纠偏样例；
  - 出现新的异常形态：加一条边界条款。
  - 每次改版都要重新跑一遍标注集，不低于上一版才上线。

## 三、代码侧要做的事（不写进 prompt）

1. **拼接前**：
   - 去掉评论里出现的 `<review_text>`、`</review_text>`、`<product_name>`、`</product_name>` 标签，防止伪造定界；
   - 平台能区分商家回复时，在进 prompt 前就剥离；
   - 超长评论截断，并在末尾加"……（已截断）"。
2. **解析**：只取回复里最后一个 json 代码块；解析失败就重试一次，仍失败则转人工。
3. **校验**：
   - 字段齐全、取值在枚举内；
   - `other_reason` 只在 `other` 时非空；
   - `problem` 和 `evidence` 不超长；
   - `issues` 不超过上限。
4. **归类复算**：有 complaint 必须是 `negative`；没有 complaint、有 suggestion 必须是 `suggestion`；`positive` / `other` 的 `issues` 必须为空。不一致时按复算结果走，并记日志。
5. **evidence 校验**：去掉空白后，必须是评论原文的子串；不是就标记"疑似编造"，转人工。
6. **路由**：
   - `negative` 推客服，含 `safety` 的置顶提醒；
   - `issues` 里的 suggestion 和各类 complaint 按 `aspect` 汇总给产品；
   - `other` 不进好评或差评统计。
