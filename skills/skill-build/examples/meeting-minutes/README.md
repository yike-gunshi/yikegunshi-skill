# 示范：一件天天重复的活 → 一个做好、测过的 Skill

日期：2026-10-22 · 使用的 Skill：skill-build

## 给了什么

只有一句话（原文见 [input/需求.md](input/需求.md)）：

> 每次开完会，我都要把会议录音的转写稿整理成会议纪要：结论、待办（谁、什么时候做完）、没谈拢的问题。能不能做成一个 skill？

没有纪要模板，没有转写稿样本，也没有别的材料。

## 用户会怎么说这句话

这句话本身就是最自然的说法：描述一件天天重复的活，顺口问一句"能不能做成一个 skill"。skill-build 的触发说明专门覆盖这种情况，哪怕用户没说"帮我做个 skill"，只描述了一件重复的活，也会接过来。同类的说法还有：

- "开完会整理纪要太烦了，能不能让 AI 每次都按一个样子整理？"
- "帮我把'转写稿变会议纪要'这个流程沉淀下来"

Skill 做好之后，日常这样用它（评测里用到的说法）：

- "刚开完会 累死 妙记导出来了在 transcripts/周会1019.txt 帮我整理下纪要 发群里那种 待办别漏了"
- "transcripts/客户对齐会.txt 你帮我看看，会上到底定了啥，谁要干啥，我怕漏了"
- "这份妙记太长了我不想看，给我个能直接转发给参会人的版本"

## 怎么跑的

在 Claude Code 里调用 skill-build，把这句话原样作为输入。Skill 按自己的固定流程走：

1. 判断值不值得做成 Skill；
2. 访谈，把没想清楚的地方问出来；
3. 写设计文档，过完备性门禁，任何一条不过就回去接着问；
4. 写 SKILL.md，跑体检脚本；
5. 造评测集，跑"用这个 Skill"和"不用"的对照；
6. 先归因再修改，每轮都要删掉点东西。

演示时，提需求的人由 AI 按一份事先写好的场景设定扮演：一个普通公司的项目负责人，每周开几次会，用飞书妙记或类似工具拿到转写稿。场景设定没覆盖到的问题，按 Skill 写明的默认做法回答，下面逐条标注「演示时由 AI 按默认确认」。

**值不值得做**：值得。这件活会反复做；容易和长得像的活混在一起（播客笔记、课程导图、用户访谈同样吃转写稿）；口径要每次一致（什么算"定了"、负责人没说清怎么写）。也考虑过每次手贴一段提示词、扩展已有的播客笔记 Skill、写进全局说明，都不如单独做一个，理由写在 [设计文档](output/设计文档.md) 第 0 节。

**做多重**：轻档，只交付一个 SKILL.md。这是 Skill 对"一个人自己用、不接任何外部系统"这类需求的默认档。但纪要写错的代价不低——错的结论发到群里会被照着执行——所以评测按完整档补做了"用和不用"的对照。Skill 允许只加评测、不加大 SKILL.md 本体。演示时由 AI 按默认确认。

## 访谈问了什么

三轮，每轮不超过三个问题。

**第一轮：需求与场景**

| 问题 | 回答 |
|---|---|
| 这件事你多久做一次？转写稿从哪来？ | 我是项目负责人，每周开几次会，用飞书妙记或类似工具拿到转写稿。 |
| 纪要最后给谁看？他们打开第一眼要看到什么？ | 发到群里给参会人看，要一眼看到结论和待办。 |
| 什么算整理错了？哪种错你最怕？ | 最怕把没定的事写成定了；还有漏掉待办。 |

**第二轮：输入与约束**

| 问题 | 回答 |
|---|---|
| 转写稿一般长什么样？ | 口语化，有人名，有跑题，有很多"嗯""啊"。 |
| 会上没说清谁负责、什么时候做完，纪要里怎么写？ | 待办必须有负责人，没说清负责人的要标出来，不要猜。截止时间演示时由 AI 按默认确认：照原话写；知道会议日期时，"周五""下周一"在括号里补上日期；"尽快""回头"写"未说定"，不替人定日期。 |
| 要不要自动发群、建任务、进日历？输出什么格式？ | 不接任何外部系统，输出 Markdown 就行。 |

**第三轮：边界、失败与档位**

| 问题 | 回答 |
|---|---|
| 有没有长得很像、但不该交给它的活？ | 演示时由 AI 按默认确认：播客、课程、用户访谈的转写稿，多份纪要汇总成周报，会前写议程，拿纪要写跟进邮件，只把逐字稿洗干净——都不归它。它只管"一场会的转写稿变成一份纪要"。 |
| 转写稿质量差时怎么办？比如只有"说话人1、说话人2"，人名前后识别得不一样，稿子中途断了。 | 演示时由 AI 按默认确认：只有编号就照写编号，不替人对上真名；人名两种写法照抄，列进"会后需确认"；稿子不完整就在开头注明，已有部分照常整理。 |
| 这个 Skill 大概多少人用？用错了有什么后果？ | 就我自己用，每周几次。用错的后果是群里的人照着错的结论干活，漏掉的待办没人做。 |

## 代确认了哪些门禁

写 SKILL.md 之前要过六条完备性门禁，任何一条不过就回去接着访谈。

| 门禁 | 结果 | 怎么过的 |
|---|---|---|
| 能说出至少三个"很像但不该触发"的请求 | 通过 | 列了五个：播客学习笔记、用户访谈提炼、只清洗逐字稿、多份纪要汇总周报、"把这件事做成 Skill"。依据的访谈回答演示时由 AI 按默认确认 |
| 说得清不处理什么、交给谁 | 通过 | 七类请求各有去处：交给播客笔记、导图、造 Skill 这几个已有的 Skill，或者直接做 |
| 每个必出的部分都对应一条判分标准 | 通过 | 轻档本可以不查；因为补做了评测，结论、待办、没谈拢、会议信息逐条对上了判分标准 |
| 用到的工具，每个字段都确认过 | 不适用 | 这个 Skill 不调用任何工具 |
| 至少五条真实、带细节的请求样本 | 通过 | 写了六条，像真人会打的字：带文件路径、口语、中英混说、直接粘贴转写文本 |
| 说得清失败了怎么办 | 通过 | 读不到文件、稿子不像会议、稿子中断、只有说话人编号、人名写法不一致都写了处理。依据的访谈回答演示时由 AI 按默认确认 |

门禁之外，还有这几处由 AI 按默认确认：

- 做多重：轻档，评测补做对照（见上文）。
- 待办用列表不用表格：列表贴到聊天窗口和文档里都能读。
- 结论不附原话，只写谁拍的板；负责人待定的待办附上原话，方便当事人认领。
- 评测题：Skill 要求造完拿给用户逐条确认，演示中由 AI 代为确认。

## 得到了什么

一个叫 `meeting-minutes` 的 Skill，只有一个 SKILL.md。它让模型像一个靠谱的项目助理那样整理纪要：

- **两个方向相反的偏好**：结论宁缺——拿不准算不算定了，就放进"没谈拢"并写出倾向；待办宁全——跑题时、散会前顺口派的活也捞出来。理由写在 Skill 里：错写一条结论会有人照着去做，漏写一条最多有人在群里问一句。
- **判"定没定"有具体信号**：只有倾向、有条件的暂定、要请示会外的人、当场有人保留意见，都不算定了；会上改过口的以最后一次为准；定了的也只写说定的那部分，不替它补适用范围和生效时间。
- **负责人只写会上点名或自己认领的人**：主语是"我们""销售那边"、没人接的问句、点了名但对方没应下，都标"负责人待定"并附原话；只有说话人编号就照写编号，不猜是谁。
- **截止时间照原话**，没说就写"未说定"，不替人估日期。
- **固定的输出骨架**：会议信息、结论、待办、没谈拢的问题，命中时再加"会后需确认"。负责人写在每条待办的最前面，群里的人扫一眼就找到自己。
- **三条红线**：没拍板的事不写进结论；不替人认领待办、不编截止日期；不写转写稿里没有的人名、数字和承诺。

## 用和不用的对比

用五份虚构的会议转写稿出题，每份都埋了陷阱：只表了态没拍板的事、会上改过口的方案、改派过的活、散会前顺口一句派的活、没人认领的活、前后对不上的数字。同一句请求，"用这个 Skill"和"不用"各跑几遍，再用两种方式打分：一个评委对照标准答案逐条判；另一个评委扮演群里的参会人，不告诉它哪份用了 Skill，只问哪份更能直接拿来用。

**该用的时候用不用得上**：该用的请求每次都用上了，包括只说"帮我理一下发群里"这种很隐晦的说法；长得像的请求一次都没被它抢走——播客笔记交给了播客笔记的 Skill，课程导图交给了导图的 Skill。

**纪要写得好不好**（下面说的是迭代后的版本；首版的结果在评测报告里，结论方向一样）：

- **差别集中在一件事上：不把没定的事写成定了。** 不用 Skill 时，将近一半的纪要把会上没拍板的事写进了"结论"，比如把销售随口提的"今年经销商扩到一百家"当成了定论。用 Skill 时只出过一次类似失误（给一条结论补了会上没说的适用范围），迭代加了一条规则后没再出现。
- **其余多数方面两组打平。** 不用 Skill 的模型自己也会分三块、会把散会前派的活捞出来、会把没人认领的活标出来、会提醒前后矛盾的数字。这说明对这个模型来说，那些规则本来就是它的默认做法。
- **按题看**：五道题里，用 Skill 在一道上明显更好，三道略好，一道和不用基本持平。
- **扮演参会人的评委**：五道题里每道都是用 Skill 的版本多数胜出。但逐份看，也有几次它更喜欢不用 Skill 的版本，理由多是"待办用表格更好扫"，还有一次是 Skill 版本把会议日期的星期几写错了。
- **代价**：用 Skill 每次要多读一段说明，整理一份纪要慢几秒钟。

**要坦白的局限**：转写稿是 AI 写的几分钟短会，陷阱也是自己埋的；真实的一小时会议还没测。只用了一个模型。触发评测的请求和标准答案都没经过真实用户确认。

### 同一场会，两份纪要的"结论"

秋季新品发布会协调会：会上真正拍板的只有场地；发布日期研发说"心里没底，周四给准话"；经销商扩到一百家只是销售的提议，没人表态。

用 Skill：

```markdown
## 结论

1. 发布会场地定为滨江会展中心 B 厅，可容纳 300 人、地铁直达，便于外地经销商（周岚拍板，郑佳、吴凯均无异议）
```

不用 Skill（节选，省略了第 2 条下面一行背景说明）：

```markdown
**一、已定结论**

1. **场地确定：滨江会展中心 B 厅**。容纳 300 人，地铁直达，方便外地经销商。备选的城西酒店宴会厅因停车位少被否。
2. **发布会日期暂定 11 月 15 日**，但尚未最终锁定——研发对固件稳定性没把握，周四给准话（详见"三"）。
3. **经销商邀请规模扩到 100 家左右**（去年 60 家），重点增加二三线城市。
4. **档期采取两头占的策略**：15 号和 22 号都先占上，为日期变动留退路。
```

不用 Skill 的版本里，第 3 条会让人照着一百家去发邀请函；用 Skill 的版本把日期和规模都放进了"没谈拢的问题"。两份全文分别在 `output/评测/基线对照/生成/with-v2/T2-r3.md` 和 `without/T2-r2.md`。

## 过程里值得一看的地方

- **评测脚本自己出过两次错，都在算分前抓了出来。** 一次是分组判断写错，"不用 Skill"那组也拿到了 Skill——试跑时两组的纪要格式一模一样，才查出来。另一次是检查骨架的脚本没认出"未谈拢"这种写法，把不用 Skill 一组的正常纪要判成缺了一块。Skill 的规矩是"健康样本上报错，先怀疑脚本"，修了再算。
- **迭代时删掉了一整步。** 首版有一步"回头再扫一遍查漏的待办"，评测显示两组找待办都一样全，这一步没起作用。删掉再测，分数没掉。
- **首版里有一句没核实的说法被改掉了。** 首版写"群聊里表格常常显示不出来"，这是没验证过的平台说法，迭代时改成了不下断言的理由。
