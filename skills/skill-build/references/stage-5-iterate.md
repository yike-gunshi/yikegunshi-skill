# S5 迭代

这一段是整个循环的心脏。发现问题然后改，只是它的一半；另一半是**怎么改才是对的**。

## 1. 结果分析

聚合分数会掩盖模式。逐条看：

- **无区分度考点**——有没有 skill 都拿满分。淘汰考点，同时把对应的 SKILL.md 章节列为候选删减
- **高方差用例**——同一条 query 多次跑分数波动大。通常说明指令在那里有歧义
- **系统性失分**——多条 query 在同一个考点上一起掉。这是真问题，优先修
- **单点失分**——只有一条 query 掉。先怀疑是 query 的问题
- **时间/token 的 tradeoff**——质量涨了多少，代价涨了多少

## 2. 归因三分

**不是所有失分都该改 skill。** 动手前先分类：

| 根因 | 信号 | 怎么处理 |
|---|---|---|
| **skill 的问题** | 多条 query 在同一考点系统性失分；transcript 显示模型误解了某条指令 | 改 skill |
| **query 集的问题** | 只有某条 query 掉；这条 query 本身有歧义或不真实；它测的东西超出了 skill 的声明边界 | 改 query 集，别改 skill |
| **考点的问题** | 考点标准模糊、无区分度、和另一条考点重复、判分依赖 judge 的主观偏好 | 改考点 |

跳过这一步直接改 skill，会把 query 集和考点的毛病一起焊进 skill 里，表现是 skill 越来越长、分数越来越好看、真实用户的体验没变。

## 3. 读 transcript

只读最终输出会漏掉一半信息。翻执行轨迹，找两样东西：

- **无效步骤**——模型在哪浪费了时间做无用功。导致这个行为的那段指令是候选删减对象。删掉再跑一次，分数不掉就是净赚
- **跨用例的重复劳动**——如果三个测试用例的执行过程里模型都各自独立写了一个类似的脚本，这是强信号：**那个脚本该被 skill 自带**。写一次放进 `scripts/`，省掉未来每次的重复造轮子

## 4. 修改

### 泛化，不要过拟合

这个 skill 会被用无数次。你和用户只在几个例子上来回迭代，是因为这样跑得快、用户对这几个例子门儿清。**但如果它只在这几个例子上有效，那它毫无用处。**

具体地：

- 别做琐碎的针对性修改（"遇到武汉的时候要提三镇跨江"）
- 别用加一条压迫性 MUST 的方式解决问题
- 遇到顽固问题，换个比喻、换种表述、换个工作模式来描述——试错很便宜，说不定就撞上一个绝妙的表述

判据：一条新加的规则，如果只对测试集里某一条 query 有意义，它就不该进 SKILL.md。

### 每轮必须有删减动作

只做加法的迭代是在把 skill 推向失效。每一轮至少删掉一样东西：一条不拉动效果的规则、一个没人读的 reference、一段重复的说明。

删了跑一次评测，分数不掉就是对的。分数掉了再加回来，这时候你知道它为什么在那儿。

### 解释 why

用户的反馈常常很短，甚至带着火气（"这输出也太啰嗦了"）。别机械地翻译成一条禁令加进去。先理解他为什么这么说、他期望的是什么，把这份理解注入指令。

- ❌ 加一条"禁止输出超过 500 字"
- ✅ 改成"这个场景用户是在路上用手机看的，读完比读全重要。信息压不下来时按这个顺序删：延展 → 备选 → 每条论据的第二个例子"

### 改完的验证

改进已有 skill 前**先 `cp -r` 快照**。跑对照的时候 baseline 用旧版，直接回答"新版真的更好吗"。

盲评：两版输出交给独立 agent，不告诉它谁是谁。

## 5. 停止条件

三个中的任何一个：用户说满意 / 反馈全为空 / **不再有实质进展**。

第三个最容易被忽略。连续两轮改动的分差都在噪声范围内，就该停下来发布，把精力放到扩大测试集或者下一个 skill 上。

首个版本只求"可路由的基线"，然后明确列出 3 个最高价值的下一步方向，避免四面八方同时膨胀。

## 6. 迭代记录

每轮记一行：改了什么、为什么改、分数怎么变、删了什么。

这份记录的用处在下一次——半年后有人问"这条规则为什么在这儿"，记录能回答；没有记录，那条规则就永远删不掉了。
