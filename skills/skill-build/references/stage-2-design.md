# S2 设计

这一份写给**人**看——业务方确认边界、研发确认 tool、评测同学确认考点。语言可以讲权衡、讲理由。翻译成模型读的祈使句是 S3 的事。

设计和撰写分开的理由：两者失败的长相完全不同。设计失败是"边界没对齐，做出来不是业务要的"；撰写失败是"边界对了但模型读不懂、不遵守"。混在一起做，会用改措辞去解决其实是没想清楚的问题。

模板：`assets/design-doc-template.md`。轻档只需 2.1–2.4。

## 2.1 要解决的问题

一句话：这个 skill 替用户完成了什么他原本要自己做的事。

写不出一句话，说明 S1 没收够料，回去。

## 2.2 定位与边界

**定位要有人格和立场，不只有范围。** 范围只能覆盖你想到的情况；人格能让模型在没预料到的情况下推断出正确行为。

三段式：

```
定位：<一句话说它是什么形态的产出> + <像什么角色> —— <把什么讲透>
核心立场：<这个场景里用户真正要的是什么> 所以 <产出的组织方式跟着变成什么>
范围：<给定什么输入，处理什么> 一次只处理 <粒度>
```

一个够格的例子：

> 定位：地方美食·实体推荐类消费决策 Top1 卡片。像一个当地土著朋友——把「这个城市/这个品类，换成是你先吃哪家」讲透：先给明确首选 + 适合谁 + 一句话避坑，再用本地人、回头客的亲身经验解释取舍，不把一份大而全的清单甩回给用户。
>
> 核心立场：经验决策场景里，用户要的是来自和自己相似处境（本地/外地、独食/请客、能否吃辣）真实人群的亲身经验。所以产出是替用户从真人经验里收敛出「先看哪个」，每条结论都能追溯到同画像真人的原声佐证。
>
> 范围：给定一个城市/品类/店名范围的美食实体推荐。一次只处理一个 query。

注意它做到了什么：说清了**不做什么**（不甩清单）、**为什么**（用户要的是同画像经验）、**判据**（每条结论可追溯到原声）。这三样让模型能自己推断边缘情况。

边界要**显式列出不处理什么、该交给谁**：

```
不处理 X，命中则交给 <哪个 skill / 什么通用能力>
```

"别的都不处理"不合格。门禁要求能说出至少 3 个"很像但不该触发"的 query。

## 2.3 触发与意图路由

分成两层，别混：

| 层 | 管什么 | 写在哪 |
|---|---|---|
| 触发 | 进不进来 | frontmatter 的 description |
| 路由 | 进来之后走哪条线 | SKILL.md 正文 |

**触发层**在这一步只需要产出素材：应触发的 query 例句、不应触发的 near-miss 例句、容易抢活的隔壁 skill 是谁。措辞打磨留到 S3。

**路由层**按意图强度分流，不同强度给不同的应答粒度：

| 意图 | 长什么样 | 应答 |
|---|---|---|
| 强意图 | 需求完整、约束明确 | 完整答案，走全流程 |
| 弱意图 | 只有方向没有约束 | 简答，给骨架不铺细节 |
| 潜在意图 | 用户在问别的，但明显需要这个 | 简答 + 反问确认要不要展开 |

分流规则要能落到可判断的信号上（query 里有没有出现具体对象、有没有时间/预算约束），"看起来很想要"不是信号。

## 2.4 输出框架

固定骨架 + 必出模块 + 触发式模块。

- **固定骨架**：锁死顺序，任何 query 都按这个结构出，不走动态逻辑。写清"哪几段是硬骨架、顺序不可增删改"
- **必出模块**：几乎都出。每个必出模块写清入选条件和内部结构
- **触发式模块**：命中才出。写清触发条件，以及命中多个时怎么排序取舍

**每个必出模块都要能对应到一条评测考点。** 对不上的模块是拍脑袋定的，删掉或者补考点——这是完备性门禁的第 3 条，也是防止输出框架无限膨胀的唯一有效约束。

骨架和模块越多，模型遵循度越低。定完数一下总数，超过 8 个模块就该问"哪几个能合并"。

## 2.5 执行流程

分几步、每步调什么工具、每步的输入输出。按这个骨架写：

背景 · 角色 · 场景 · 关键步骤 · 工具调用 · 输入输出

每一步要能回答"这一步失败了怎么办"。门禁第 6 条查的就是这个。

## 2.6 辅助资源

哪些内容该做成模板、脚本、参考文件。判断依据：

- 每次都要重写一遍同样的代码 → `scripts/`
- 模型需要查阅但不必每次加载的长文档（字段全表、排版语法、组件规范、参考范例）→ `references/`
- 会被复制进最终产出的东西（模板、图标、字体）→ `assets/`

这一步先列清单，实现放到 S3。

## 2.7 输入输出定义

预期收到什么形态的 query，产出什么形态的内容。至少 5 条真实的、带细节的 query 样本——门禁第 5 条。

"用户会问旅游攻略"不算样本。样本要长得像真人打的字。

## 2.8 上下文分层规划

在写之前就把话说清楚：什么进 SKILL.md，什么外移。

| 层 | 加载时机 | 放什么 | 预算 |
|---|---|---|---|
| metadata | 永远在上下文 | name + description | 最贵，只放触发相关 |
| SKILL.md 正文 | 触发时全量加载 | 定位边界、触发、流程骨架、红线、输出骨架 | < 500 行 |
| references/ | 按需读入 | 长表、语法规范、范例、政策 | 不限，但要在 SKILL.md 里点名何时读 |
| scripts/ | 按需执行，代码不进上下文 | 确定性重复逻辑 | 不限 |

不做这一步的后果是可预测的：SKILL.md 一路长到 800 行，中间的规则被稀释，然后开始往里加"最高优先级"，越加越长。

外移的每个文件都要在 SKILL.md 里被引用并说明何时读。建了但从没被引用的目录是装饰性目录，`scripts/validate_skill.py` 会报出来。

## 出口

八个模块写完，跑完备性门禁六条。任何一条不合格，回 S1，不往下走。
