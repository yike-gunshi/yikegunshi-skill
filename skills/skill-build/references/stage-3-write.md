# S3 撰写

把设计翻译成给模型读的指令。骨架 `assets/skill-md-skeleton.md`。

## description

**它是路由的唯一依据**，也是唯一一段无论触发与否都常驻上下文的文字。两条约束同时成立：写得够全，写得够短。

### 结构

```
<做什么，一句话> + <什么时候用它，覆盖同义说法和隐含场景> + <不处理什么，该交给谁>
```

### 写得推销一点

模型当前有明显的**欠触发**倾向——该用的时候不用。对抗它的办法是显式覆盖同义场景，并且点破"哪怕用户没明说"。

- ❌ `How to build a simple fast dashboard to display internal data.`
- ✅ `How to build a simple fast dashboard... Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a "dashboard."`

中文同理，覆盖同义词、覆盖用户描述症状但没说方案的情形、覆盖"改已有的"这类场景：

> 用户说"做个 skill""建个 skill""把这个流程沉淀下来"时用它；他只是描述了一件天天重复的活，也用——哪怕他没说 skill 三个字。改已有 skill 一样走它：不触发、写得太长、要做评测。

### 所有"何时使用"都放这里

正文里不要写"When to Use This Skill"章节。正文只在触发之后才加载，那时候触发判断已经做完了，写在那里的触发说明没有任何读者。

反过来，**执行层的禁令要移回正文**。"不许伪造用户原声""评论占比不得编造"这类内容不影响触发决策，放在 description 里是在花最贵的预算买不产生作用的字。

### 排除项

必写。"不处理什么、该交给谁"既降低误触发，也帮用户理解边界。

### 尺度

上限 1024 字符（超了包会校验失败），实际控制在 300 字符上下。写完可以用触发评测实测长短版哪个准召更高，方法见 stage-4。

### name

hyphen-case，稳定。**更新 skill 时不改名**，不要出现 `-v2`。改名会让所有 symlink 和引用静默失效。

## 正文写法

### 少堆强调词，改成解释 why

发现自己在写全大写的 ALWAYS/NEVER，或者第五个"最高优先级"，那是黄色警告。

一份文档里有 7 个"最高优先级"就等于没有优先级——模型在它们冲突时无法取舍。这里有个恶性循环：

```
规则不被遵守 → 加强调词 → 文档变长 → 长上下文里规则被稀释 → 更不被遵守 → 加更多强调词
```

唯一的出口是**缩短和分层**，加强调词只会让它转得更快。

对照写法：

| 堆强调词 | 解释 why |
|---|---|
| **禁止**加【】段标题，违反即不合格 | 不加段标题——四层结构靠段落和 emoji 已经能自然分层，加了标题会让短答案显得臃肿、像公文 |
| **必须**控制在 900 字以内，这是不可突破的底线 | 控制在 900 字以内。超过三屏用户会直接划走，这个场景里读完比读全重要。压不下来时按这个顺序删：延展内容 → 备选方案 → 每条论据的第二个例子 |

第二列除了传达同样的约束，还让模型在遇到没预料到的情况时能做出正确推断。第一列只能覆盖你想到的那些情况。

### 用祈使句

写给模型的是指令。"先解析输入，再并行取事实底座和首批评论"，不写"这一步我们需要先……"。

### 红线的准入标准

只有**违反会造成不可逆外部损害**的才配当红线，总数 ≤ 5 条。

| 类型 | 举例 | 怎么处理 |
|---|---|---|
| 事实性 / 法务风险 | 伪造用户原声、错配图片、编造价格政策、泄露凭证 | 保留红线。红线的作用是在模型犹豫时给一个不需要思考的答案 |
| 格式 / 风格约束 | 不加段标题、emoji 只用图例里那几个、引用独立成行 | 改成带 why 的说明 |
| 长度约束 | 3 屏 / 900 字 | 改成 why + 压缩策略。别写"违反即不合格"，它和"信息不足时也不应低于一屏"自相矛盾 |

已有 skill 超过 5 条红线时，逐条问"违反了会发生什么、能不能收回来"。收得回来的降级成带 why 的强建议。

### 分层控长

SKILL.md 正文 < 500 行。超了就外移，不要靠压缩措辞硬塞。

| 外移到 | 什么内容 |
|---|---|
| `references/` | 字段全表、排版语法、组件规范、参考范例、政策、长示例 |
| `scripts/` | 每次都要重写一遍的确定性逻辑 |
| `assets/` | 会被复制进产出的模板、图标、字体 |

多领域时按变体拆：`references/{aws,gcp,azure}.md`，模型只读相关那一个。

引用要一层深，别让 SKILL.md 指向 A、A 再指向 B。每个外移文件都要在 SKILL.md 里点名"什么时候读它"，否则模型不知道它存在。超过 100 行的 reference 在开头加一个目录。

### 不要建的文件

README.md、INSTALLATION_GUIDE.md、QUICK_REFERENCE.md、CHANGELOG.md。skill 目录只装模型干活需要的东西；建包过程的说明、给人看的文档放到仓库层面。

## tool 信息（完整档）

S1 盘出来的字段表直接落进 SKILL.md 或 `references/tools.md`。判断依据是长度：三个 tool 以内、字段不多就留在正文，字段全表外移。

每个 tool 写清：什么时候调、入参怎么构造、返回哪些字段有用、**哪些字段本 skill 不使用**、失败时降级到什么。

## 输出约束

严格要求用模板块，写"按这个结构输出"并给出完整骨架。需要留判断余地的写"这是一个合理的默认结构，按情况调整"。

输出质量依赖于看范例的（写作类、风格类），给 Input/Output 配对示例，比描述有效得多。示例要标清"学语气和分层，别照搬内容"。

## 自检

可以写，但要明白它的位置：**自检是模型的自觉行为，不可靠，替代不了评测**。它能捞回一部分低级遗漏，捞不回系统性问题。真正的把关在 S4。

## 写完

跑体检：

```bash
python3 scripts/validate_skill.py <skill目录>
```

查结构、frontmatter 合法性、正文行数、强调词密度、红线条数、装饰性目录。有 warning 先改，改不了的写清楚为什么留着。
