# S4 评测

两个问题：它好不好，以及**不用它会差多少**。第二个问题决定这个 skill 该不该存在。

轻档只做第 1、2 节。

## 1. 造 query 集

评测集的质量决定评测的上限。烂的 query 产出烂的 description，后面所有工序都白做。

### 质量标准

真实用户会打的字。要有文件路径、工作背景、列名、公司名、URL、一点前情。有的小写、有缩写、有错别字、有口语。长度混搭。**聚焦边缘情况而非明确情况**。

- ❌ `帮我总结评论区`
- ✅ `刚发的那条视频评论区好像吵起来了，你帮我看看在吵什么，主要是不是都在骂价格那段。链接我发你 https://...`

### 正例覆盖

- 同一意图的不同措辞（正式的、随意的）
- 用户没明说 skill 名或文件类型但明显需要的
- 不常见但合法的用法
- 与其他 skill 竞争、但本 skill 该赢的

### 负例必须是 near-miss

和 skill 共享关键词或概念、但实际需要别的东西的请求。相邻领域、朴素关键词匹配会误触发的模糊措辞。

**明显无关的负例什么都测不出来。** "写个斐波那契函数"作为 PDF skill 的负例毫无价值。做旅游攻略 skill 时，"上海哪家本帮菜好吃"才是有用的负例——它共享"上海"和"推荐"，但归美食 skill 管。

### 数量与确认

8-10 条正例 + 8-10 条负例。造完**拿给用户逐条确认**，这一步别省。

模板：`assets/trigger-eval-template.json`

### 别把工具限死，否则触发率虚高

跑触发评测时给模型的工具集要接近真实使用环境。只留一个 `Skill` 工具，等于抹掉了"我自己动手就行"这条路——而那恰恰是欠触发的成因，数字会系统性偏高。

实测过一次：同一套题，只给 `Skill` 时正例召回 100%，放开只读工具（Read/Grep/Glob）后掉到 80%，掉下去的两条都是模型改用 Read 直接去翻文件了。**放开只读工具测出来的才是真的。**

### query 必须够有分量

模型只在自己搞不定的任务上才去查 skill。"读一下这个文件"这种一步就能干完的请求，description 写得再完美也不触发——用它当测试用例，测的是模型的偷懒倾向，不是 description 的质量。**复杂、多步、专门化的 query 才会稳定触发。**

## 2. 触发评测

- 每条 query 跑 **3 次**取触发率，单次结果有随机性
- 60% train / 40% test 分割
- 改 description 时只看 train 的失败案例，**按 test 分数选最终版本**，避免调出一个只在训练集上好看的 description

要验证 description 长短版哪个好，就是在这里做：同一套 query，长版和短版各跑 3 次，比 test 集上的准召。

多个 skill 共存、怀疑抢活时，把隔壁 skill 的正例也放进来当负例，看会不会被抢。

## 3. 基线对照（完整档）

**这是整套评测里最重要的一环，也是最容易被跳过的一环。**

同一批 query 跑两遍：

| 场景 | 对照组 |
|---|---|
| 新建 skill | 完全不给 skill |
| 改进已有 skill | 旧版快照（动手前先 `cp -r`） |

用同一套考点打分，比分差。

判读：

- **分差大** → skill 在这条考点上产生了真实增益
- **分差 ≈ 0** → 两种可能：这条考点没有区分度，或者这个约束本来就是模型的默认行为。对应的 SKILL.md 章节是候选删减对象

没有基线对照，就永远不知道 skill 里哪 30% 的文字是纯粹的上下文浪费。

跑的时候把 with 和 without 一起发出去，别先跑一半——中途停下来会让两组的环境不一致。

## 4. 考点评测

分档给分，不用 pass/fail 二值。每条考点写清：维度、总分、得满分的条件、得零分的条件、主观还是客观。

模板和 judge prompt：`assets/rubric-template.md`

### 三层裁判

| 考点类型 | 谁来判 | 为什么 |
|---|---|---|
| 客观可程序化（组件召回、字数、加粗数量、字段存在性） | **脚本** | 快、稳定、跨迭代可复用。让 LLM 用眼睛数加粗数量是浪费 |
| 主观（真人表达感、文采文风、有用性） | LLM 多次采样取中位数 | 单次打分方差大 |
| 全部 | 10% 人工抽检 | 得有人看 judge 判得对不对 |

### judge 的第二职责

除了给输出打分，judge 还要**批判考点本身**。在一条弱考点上通过比没测更糟——它制造虚假信心。

judge 还应**提取输出里的隐含声明并验证**：

- 事实性声明："这家店人均 80"
- 过程性声明："我查了 3 个平台"
- 质量性声明："所有景点都配了实拍图"

验证不了的声明要标出来。这一条对"真实性"维度是直接的能力升级——伪造原声和错配图片正是这类 skill 最怕的失败。

判 PASS 要求**真实完成任务**，不是表面合规。文件名对但内容是空的，算 FAIL。

## 5. 性能

`total_tokens` 和 `duration_ms`，**每个 run 一结束立刻记**。这是唯一能拿到这些数据的时机，过了就没了。

skill 通常会让任务变慢变贵。要看这个代价换来的质量提升值不值。

## 6. 考点自身审计

找出**有没有 skill 都拿满分**的考点。它们没有区分度，占着评测预算却不产生信息，淘汰。

同时标记**高方差用例**（同一条 query 多次跑分数波动大）。方差大通常说明 skill 指令在那个地方有歧义，是 S5 的重点排查对象。

聚合和审计跑脚本：

```bash
python3 scripts/score_rubric.py --with with.json --without without.json
```

它输出每条考点的 with/without 均值、分差、方差，并把分差小于阈值的考点标成 `NO-SIGNAL`。

## 7. 盲评（可选）

两个版本的输出交给一个独立 agent，**不告诉它谁是谁**，只让它比质量。出结果后再揭盲，分析赢家赢在哪、输家输在哪。

比直接问"新版是不是更好"可靠——知道哪个是新版的评委会倾向于说新版更好。

## 产出

query 集 + 考点表 + 评测报告，交给评测同学。报告里写清跑了多少条、跑了几次、哪些考点无区分度、性能代价多少。

**没实际跑过的不写进报告。** 跑了几条说几条。
