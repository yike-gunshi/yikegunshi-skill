# 反模式库

S0 判定存疑时、S3 自查时、S5 想加东西时读。

## 一、不该做成 skill

| 反模式 | 长什么样 | 该做什么 |
|---|---|---|
| **一次性需求** | "帮我分析下这份数据" | 直接做 |
| **纯讲解** | "跟我讲讲 RAG 是什么" | 直接回答 |
| **纯总结 / 纯翻译** | "把这篇文章总结一下" | 直接做 |
| **头脑风暴** | "帮我想几个方向" | 直接聊 |
| **把背景知识包装成 skill** | 内容全是"我们公司的 X 系统是这样的" | 写进 CLAUDE.md 或项目文档 |
| **缺的是能力不是流程** | 要查数、要调没有的接口 | 加 tool。skill 是编排层，编排不了不存在的能力 |
| **已有 skill 能覆盖** | 和现有某个 skill 的边界高度重叠 | 扩展那个 skill，多一个 skill 就多一个路由竞争者 |
| **只是想让输出稳定** | 单条指令的措辞问题 | 改 prompt，或走 prompt-craft |

**讲解需求 vs 打包需求**这一对最容易混。"帮我总结这个流程"（要总结）和"把这个流程做成 skill"（要建包）是两件事，问清楚再动手。

## 二、写作反模式

### 强调词膨胀

一份 1998 行的 skill 里出现 318 个强调词——必须 110 次、禁止 78 次、最高优先级 7 次、不可突破 4 次——平均每 6 行一个。

7 个"最高优先级"等于没有优先级，模型在它们冲突时无法取舍。根因是文档太长把规则稀释了，解法是缩短和分层。加更多强调词只会把文档推得更长。

自查：`grep -c "必须\|禁止\|严禁\|绝不\|一律\|强制\|不得\|最高优先级\|不可突破"`，或直接跑 `scripts/validate_skill.py`。

### 红线通货膨胀

12 条"违反任何一条即不合格"。逐条问"违反了会发生什么、能不能收回来"，收得回来的降级成带 why 的强建议。留下来的应该 ≤ 5 条。

### 自相矛盾的约束

"超过 900 字视为输出不合格" + "信息不足时也不应低于一屏"。模型遇到信息真的不足的情况时无法取舍。写约束时过一遍：有没有另一条规则会和它打架。

### 正文里写"何时使用"

正文只在触发之后才加载，那时触发判断已经做完。写在正文的 When to Use 没有读者。触发信息全部归 description。

### description 里写执行禁令

"不许伪造原声"这类内容不影响触发决策，放在 description 里是在花最贵的常驻预算买不产生作用的字。移回正文。

### 靠压缩措辞控长

SKILL.md 超过 500 行时把句子改短，只会得到一份又长又难读的文档。该做的是外移到 references/。

### 写死在特定示例上

"遇到武汉的时候要提三镇跨江"。这类规则只对测试集里那一条 query 有意义，是过拟合的典型长相。

## 三、结构反模式

| 反模式 | 为什么坏 |
|---|---|
| **装饰性目录** | 建了 `references/` 但 SKILL.md 从没引用它，模型不知道它存在。`validate_skill.py` 会报出来 |
| **默认建全套空文件夹** | 轻档 skill 一个 SKILL.md 就够 |
| **给一次性 skill 加评测** | 评测只在复用量大到路由错误有代价时才划算 |
| **为了显得成熟加治理文件** | owner、审查周期、成熟度评分对个人 skill 是纯负担 |
| **多层引用** | SKILL.md → A → B。引用保持一层深，全部从 SKILL.md 直接链出 |
| **README / CHANGELOG / INSTALLATION_GUIDE** | skill 目录只装模型干活需要的东西，建包过程的说明放仓库层面 |
| **改名带版本号** | `research-helper` 改成 `research-helper-v2`，所有 symlink 和引用静默失效 |
| **复制成真文件副本** | 同一个 skill 在多处各存一份，版本必然漂移。用 symlink |

## 四、评测反模式

| 反模式 | 为什么坏 |
|---|---|
| **负例写得明显无关** | "写个斐波那契函数"当 PDF skill 的负例，什么都测不出来。负例必须是 near-miss |
| **query 太轻** | "读一下这个文件"这种一步就能干完的请求根本不会触发 skill，测的是模型的偷懒倾向 |
| **单次采样定结论** | 触发和打分都有随机性，至少跑 3 次 |
| **按 train 分数选 description** | 调出一个只在训练集上好看的版本。按 test 选 |
| **跳过基线对照** | 不知道 skill 里哪些约束真的在起作用，也不知道它值不值得存在 |
| **让 LLM 数加粗数量** | 客观可程序化的考点走脚本，更快更稳更可复用 |
| **没人审 judge** | judge 判错了没人知道。10% 人工抽检 |
| **留着无区分度考点** | 在弱考点上通过比没测更糟，它制造虚假信心 |
| **知道谁是新版的 A/B** | 评委会倾向于说新版更好。盲评 |
| **报告写没跑过的东西** | 伪造证据比没有证据更糟 |

## 五、迭代反模式

| 反模式 | 为什么坏 |
|---|---|
| **所有失分都改 skill** | 有些是 query 的问题、有些是考点的问题。先归因三分 |
| **只做加法** | 每轮必须有删减动作，否则 skill 走向失效 |
| **只读最终输出** | 漏掉执行过程里的浪费步骤和重复劳动 |
| **把用户的火气直译成禁令** | "太啰嗦了"翻译成"禁止超过 500 字"，丢掉了背后的判断依据。解释 why |
| **无限打磨** | 连续两轮分差都在噪声内就该停。首版求可用基线，然后列 3 个下一步 |
| **改之前不快照** | 跑不了对照，也回滚不了 |
