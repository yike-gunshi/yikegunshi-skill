# S0 该不该做 · S1 收料

## S0 资格审查

### 四选一，够一条就继续

| 条件 | 怎么问出来 |
|---|---|
| 会被重复使用 | "这件事你一个月大概做几次？下个季度还会做吗？" |
| 容易被路由错 | "有没有别的需求跟它长得很像？搞混了会怎样？" |
| 有确定性脚本能省力 | "这里面有没有哪一步是每次都一模一样、纯机械的？" |
| 需要治理 / 跨会话统一 | "这个口径要不要所有人都一致？有没有人会来审？" |

一条都不占，就走拒绝出口。

### 拒绝出口怎么说

别只说"不建议做"。给出替代方案并说清代价：

| 情况 | 替代 |
|---|---|
| 只想让模型知道一些背景知识 | 写进 CLAUDE.md 或项目文档 |
| 只是一次性的分析 / 总结 / 翻译 | 直接做，不建包 |
| 已有 skill 的边界能覆盖它 | 扩展那个 skill 的正文，或加一份 reference |
| 缺的是能力不是流程（要查数、要调接口） | 加一个 tool，skill 是编排层，编排不了没有的能力 |
| 只是想让模型输出稳定一点 | 改 prompt，或走 prompt-craft |

反模式清单见 `antipatterns.md`。

### 业务场景的特殊情形

需求自上而下派下来、用户没有"不做"的权限时，S0 不作废，把它用在这两个问题上：

- **扩展已有 skill 是否更划算**——新建一个 skill 意味着多一个路由竞争者，两个 skill 抢活的代价常常比一个胖 skill 更高
- **边界归谁**——把"哪些请求归它、哪些归隔壁"写下来。这个决策不写下来，后期一定变成路由打架

产出：一段话，"为什么这个需求需要一个独立的 skill，而不是 A/B/C"。

## S1 收料

### 先翻历史，再开口问

对话历史里已经手工演过这个流程的（典型信号是"把刚才那套做成 skill"），从历史里提取比从零问快得多：

- 用过哪些工具，什么顺序
- 用户中途做过哪些纠正——**纠正是最高价值的信息**，它标记了模型的默认行为和期望之间的差
- 观察到的输入输出格式
- 哪一步反复返工

提取完拿给用户确认，把访谈变成"我理解得对吗"。

### 1.1 需求与场景

| 问什么 | 什么样的回答算合格 | 答不上来说明 |
|---|---|---|
| 谁在什么处境下会用到它？ | 有具体角色和场景，"运营在做选品复盘的时候" | 场景没收敛，skill 会做成一个万能助手 |
| 他现在怎么解决？哪一步最烦？ | 能说出具体的痛点动作 | 这个需求可能是拍脑袋想出来的 |
| 理想情况下他拿到什么？ | 能描述出成品的形状 | 输出框架无从设计 |
| 什么算做对了？ | 有可判断的标准 | 评测阶段会没有考点可写 |

### 1.2 已有决策与约束

已经拍板、不能推翻的东西。漏掉这一块，设计做完了才发现方向不对。

- 平台与形态（在哪跑、输出到哪、有没有富媒体组件）
- 上下游（谁调它、它的结果给谁用）
- 合规与安全（能不能引用原声、能不能给价格、要不要标来源）
- 参考对象：最多扫 3-5 个已有 skill 或产品，并且**明确记下哪些不借鉴**。不写这一条，新 skill 会把参考对象的臃肿一起抄过来

### 1.3 基建盘点（完整档）

这一块是业务场景相对开源工具的独有优势，做扎实。

产品同学常常不知道有哪些 tool 可用、每个返回什么。引导他把 schema 贴进来，然后**逐字段过一遍**，产出一张表：

| 字段 | 类型 | 本 skill 怎么用 | 用不上 |
|---|---|---|---|
| `text` | string | 评论正文，情绪归纳的主要来源 | |
| `digg_count` | int | 排序权重，取 top 决定讲什么 | |
| `is_hot` | bool | | ✓ 与热度排序重复 |

**明确列出"不使用"的字段和原因**，价值和列出"使用"的一样大——它防止模型在运行时自作主张去读那些字段，也让下一个改这个 skill 的人知道这是想过的，不是漏了。

一并确认：

- 每个 tool 的失败长什么样（超时、空结果、限流），失败时降级到什么
- 调用配额和耗时，会不会成为瓶颈
- 哪些 tool 必调、哪些看情况调

### 访谈节奏

一轮不超过 3 个问题。产品同学被一次问十条会直接放弃或者敷衍作答，敷衍的答案比没答案更危险，因为它看起来像信息。

术语先翻译再用。"评测""基线"可以直接说；"schema""断言""holdout"要先确认他懂。

产出：需求与基建清单，拿给研发确认 tool 可用性。
