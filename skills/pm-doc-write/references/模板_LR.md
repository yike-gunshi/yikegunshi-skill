# 场景模板：LR 评审文档

适用：策略、模型、链路等改动上线前的 Launch Review 文档，读者是 leader、方案 reviewer、场景与模块 owner，评审通过即合版上线。一份 LR 只覆盖一组绑定上线的改动；不绑定上线的改动拆成多份。

## 固定骨架（八段，顺序锁死，全部 H1）

1. `# Highlight`：callout（🍊），四条 bullet 封顶，顺序固定——目标、改动、效果、上线
2. `# Reviewer`：引用块，四个角色
3. `# 背景和问题定义`：H2 三节——问题发现、为什么会有这类问题、理想状态是什么样
4. `# 改动方案与详情`：每个改动一个 H2，编号排序
5. `# 评估方案与结果`：H2 两节——评测方案、评测结果
6. `# 结果分析`
7. `# 合版情况`
8. `# TODO`

## 各段写法

### Highlight

- **目标**条：解决什么问题（带问题在全量里的数量与占比，回归集链接化）、问题表现一句、根因一句
- **改动**条：多个改动用 ①② 编号并置一条，各自一句话说清从什么改成什么，尾部带测试环境名
- **效果**条：修复数与修复率（-xxpp 形式，带分子分母），判定方式链接化（评测框架 + 人工 review 明细）
- **上线**条：预期日期加粗、上线动作一句、资源或前置依赖一句
- 不进 Highlight 的：遗留问题细节、原理解释、协作口径——这些下沉到结果分析

### Reviewer

四个角色全部落到具体人（飞书发布时 @人）：直属 leader、改动方案 reviewer、对应场景 owner、对应模块 owner。发布前必须填齐，不带着待补充上会。

### 背景和问题定义

- **问题发现**：问题从哪几轮评测来（链接），落到分类表——二级问题｜数量（占比）｜判定边界。判定边界写清责任切分（如 intent 传对了才算这类），防评审时扯皮
- **为什么会有这类问题**：根因逐条 bullet，每条带出处链接；历史选型决策要带当时的数据（如耗时 +25.0%~49.0%）和结论文档
- **理想状态是什么样**：正向描述改动后的应然行为，且必须落到可评测口径——能在哪个评测框架下拿到什么档位结果

### 改动方案与详情

- 每个改动一个 H2（`## 1. 链路：旧 X → 新 Y`），标题里就把改动方向说完
- 表格承载：链路类用 改了什么｜改动前｜改动后；模型类用 维度｜说明（训练方式、时延、资源各一行）
- 提供方、对接人直接写进表格（发布时 @人）
- 只写改动本身；与本次改动无关的口径声明、免责类引用块不放

### 评估方案与结果

- **评测方案**三行 bullet：评测集（范围加链接）、环境（测试环境名加基线）、判定（评测框架加人工 review，均链接化）
- **评测结果**：先汇总表（二级问题｜总数｜修复｜修复率），合计行加粗
- 典型样例每条一张**修改前｜修改后双栏表**：cell 内 logid（行内 code）+ 回答原文完整代码块 + 底部一句归因。原文必须放全文，只写归因结论不放原文不合格
- 逐条明细外链，不塞正文

### 结果分析

- 第一段必须给出**明确的合版判断**：效果符合预期可直接合版上线，或不达标不建议合版。修复了哪类、为什么修得动（机理一句），未修复的是哪类、为什么修不动
- 后续迭代口径：短期怎么发现问题、长期专项由谁跟，出处链接化
- 机理、链路关系适合用图时配画板

### 合版情况

四条 bullet：切换 owner（发布时 @人，含依赖方动作）、切换时间（加粗日期）、对应版本（环境名行内 code，未定的斜体标注待切换后补充）、合版评估结果（未发生就显式留待补充）

### TODO

只写会真做的事，每条加粗动作名加冒号加一句展开。观察类泛项（上线后看看 xx）、纯依赖别人的事项不写。

## 数据纪律（LR 特有，逐条硬性）

- 每个数字带出处链接；修复率写 -xxpp 并带分子分母（9/15）
- 口头同步的结论（会议纪要里某人说的）默认不写；确需引用限客观陈述（时延、资源），必须挂纪要链接。效果预期类口头结论（适配 xx 后预计提升）一律不写
- 不同评测标准下的历史效果结论不与本轮混用，引用时显式声明标准不同；性能耗时数据可跨轮引用
- badcase 样例必须放改前改后的回答原文，代码块维护
- 基线写清是什么（线上旧链路），修复数的判定口径写清（端到端评测 + 人工 review）

## 精选片段（学结构和语气，别照搬内容；名称、环境名、数字均为虚构示例）

Highlight 改动条与效果条的形态：

> - 改动：① **链路**从旧搜索链路切到与主站 Top1 在线卡一致的新在线卡链路；② **模型**换成模型X（DPO 基座 + GRPO RL），测试环境 pre_env_x
> - 效果：22 条搜索 bad case **修复 14 条（-64pp）**，其中回答有误 **-60pp（9/15）**、回答质量差 **-71pp（5/7）**，判定方式为端到端 session 满意度评测 + 人工 review（均链接）

结果分析首段的形态：

> **改动有效，且能力边界清楚：**修复的 14 条集中在无依据断言、结构混乱、安全表述淡化这几类，正是 GRPO 用 rubric 做 reward 能直接打压的输出模式，未修复的 8 条几乎全是长尾事实核验，模型没查到就编一个。效果符合预期，可直接合版上线。
