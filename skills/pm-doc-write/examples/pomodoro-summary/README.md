# pm-doc-write 示范：番茄钟项目总结

给 pm-doc-write 一堆项目记录，得到一份结论先行、能直接发出去的项目总结。

- 日期：2026-10-23
- 项目：[Forge 示范项目：番茄钟网页](https://github.com/antonailog/forge-demo-pomodoro)，从一句想法用 Forge 的 Skill 一路做到合并发布、修完一个 bug

## 给了什么

- **过程记录**：番茄钟示范里每个 Skill 跑完写的一份记录（输入、过程、门禁代答、产物、问题），加上派活给 Codex 的记录和示范的需求方设定。
- **项目文档**：项目仓库里的需求讨论、PRD 和变更日志、Feature Spec、设计变更日志、工程文档和变更日志、QA 验收手册、版本记录、Bug 修复报告、功能状态，以及提交历史。
- 完整清单见 [input/来源.md](input/来源.md)。

## 用户会怎么说

「番茄钟做完了，把这些记录整理成一份项目总结，给想知道它是怎么用 AI 做出来的同事看。」

## 怎么跑的

- **本机未安装，按 SKILL.md 手动执行**：pm-doc-write 没有装进 Claude Code 的 skills 目录，Skill 工具调不到。直接读 `SKILL.md`、`references/通用约束.md` 和 `references/模板_项目总结.md`，按 SKILL.md 的 S1 到 S5 一步步走。
- **示范不读用户私有范文**：SKILL.md 提到的范文库是使用者本地的私人工作文档。这次只用模板和通用约束写，终审时也没有回范文库找手感。
- **S1 认场景与素材**：判为起草线、项目总结场景；把素材里的数字、链接、责任人逐项清点，每个数字都要能在记录或仓库文档里找到出处。
- **S2 读知识层**：读通用约束和项目总结模板。
- **S3 起草**：按模板锁死的骨架写：开头 callout、概念介绍、方法论、踩过的坑、更理想的做法、附录、草稿。模板和通用约束冲突的地方按 Skill 的规定以通用约束为准，所以在文档头加了一张结果一览表，让结论先出现。模板里为模型训练项目写的三要素（标准、样本、指标），在这个项目里换成了标准、证据、判据。
- **素材里缺的东西不补编**：项目仓库是公开的，正文链接都挂 GitHub 上的原文件；各 Skill 的过程记录还没发布，找不到可用链接，引用处按 Skill 红线标「链接待补充」。需要责任到人的地方写 Skill 名，不写人名。
- **S4 终审**：逐条过通用约束末尾的终审清单，另用脚本扫了一遍装饰符号和套话。
- **S5 确认与发布**：只交本地 markdown，不发飞书。

## 代确认的门禁

- 演示时由 AI 按默认确认：场景按项目总结处理，读者是想了解做法的同事；任务里已经给了场景、读者和素材位置，信息不足时的追问不触发。
- 演示时由 AI 按默认确认：草稿通过，不再改。
- 演示时由 AI 按默认确认：不发布。Skill 里发布是可选的最后一步，要先说清发到哪并得到确认；这次示范规矩是不发任何平台，只交本地 markdown。
- 不执行：成稿读着不像本人手笔时回范文库重写。示范不读用户私有范文，这一步跳过。
- 不触发：收录子流程。用户没说要收录。

## 得到了什么

- [output/番茄钟项目总结.md](output/番茄钟项目总结.md)：飞书就绪的 markdown（没有发飞书）。
  - 开头一屏是一句话内容和结论、结果一览表、口径说明，再放一张做出来的番茄钟截图。
  - 正文讲 Forge 是什么、人和 AI 怎么分工、每个阶段该交出什么、踩过的坑和更理想的做法；每条经验写成原则加做法、问题、优化，后面跟一张证据表。
  - 附录有各阶段耗时、示范中发现的 Skill 自身问题、给 Codex 的任务书原文和资料来源；文末草稿区留着需求方还没做的手动验证。
- 最适合截图的一屏：成稿开头，从 callout 到结果一览表和口径说明。

## 注意

- 示范里所有要用户拍板的地方都是 AI 按事先写好的设定代答的，番茄钟项目本身的门禁也一样。
- 成稿里引用的过程记录还没有公开链接，发出去之前要补上，或者改成引用项目仓库里的文档。
- 成稿的耗时按提交时间算，没有真人讨论和等待，真实使用会更长。
