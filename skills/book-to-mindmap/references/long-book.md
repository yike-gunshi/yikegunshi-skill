# 长书怎么处理

一本十章的技术书没法在一次会话里读完再动手。这份文档解决三件事：怎么读不爆上下文、中断了怎么接着干、怎么让十章读起来像一个人写的。

## 一、别把整本读进上下文

超过约五万 token 的书，禁止无界地整篇 Read。算一笔账就明白：一本两百页的书约七万五千 token，逐章重读一遍要跑二十多趟，光输入就是两百万 token。正确做法是把全文当成可查询的语料，只取当前需要的那一段。

```bash
wc -w 全文.txt                                    # 先量大小再决定怎么读
grep -n -E "^#{1,3} |^第[0-9一二三四五六七八九十]+章" 全文.txt | head -40   # 找章节行号
sed -n '120,480p' 全文.txt                        # 只取这一章
grep -c "上下文感知检索" 全文.txt                  # 声称某个概念前，先确认它真的出现过
```

最后那条是最省力的防幻觉手段：在导图里写下某个框架名之前，先 grep 一次确认作者真的讲过它。

`scripts/book_survey.py` 把前三步打包了，直接跑它。

## 二、章节切分会骗人，要交叉验证

切分按三级降级：**目录或书签 → 标题正则 → 固定长度兜底**。每一级都有坑：

- 目录条目少于三条，基本说明目录不可信，回退到正文标题
- Markdown 前缀会让常见的章节正则失效：`Chapter 1` 匹配得上，`## Chapter 1` 匹配不上。有项目因此把 35 章误判成 375 章
- 反过来，正文里的交叉引用（"第 6 章会讨论…"）会被误当成章节标题。判据是标题后面跟的是行尾、标点或大写词，跟小写延续的是行文

所以要用两套正则各跑一次对比，数字差得离谱就说明有一套错了。`book_survey.py` 已经做了这个交叉验证并会报警。

切完做一次丢字断言：各章字数之和应当等于全文字数（去掉空白后）。对不上就是切丢了内容。

## 三、进度要落盘

每章处理完立刻把结果写进 `.mindmap/state.json`，别攒在上下文里：

```json
{
  "book": "书名",
  "source": "全文.txt",
  "level": "精读替代版",
  "done": ["ch1", "ch2"],
  "spine": [
    {"ch": 1, "terms": ["上下文工程", "静态前缀"], "claim": "本章一句主张"}
  ],
  "pending": ["ch3", "ch4"]
}
```

会话中断后读这个文件就能接着干。已完成的章节不重做。

## 四、写第 N 章时要看得见前 N-1 章

这是十章读起来像一个人写的关键，也是防止第 7 章重新解释第 2 章已定义概念的唯一办法。做法是把已完成章节的骨架压缩成一份"脊柱"（spine）带在上下文里，每章 4-8 条：本章新引入的术语，加一句本章主张。

脊柱的用法必须写清楚，否则模型会把前几章的内容抄进当前章：**脊柱只用来避免重复解释和便于交叉引用，不要当成本章内容来写。**

脊柱要有上限，比如总量控制在八千字符以内，超了就滚动淘汰最早的。

## 五、章节之间可以并行

各章之间依赖很弱，适合分章并行：每章派一个子 agent 处理，只回传该章的骨架和 notes（一两千 token），主上下文只保留骨架、脊柱和进度文件。这样主上下文永远不会被原文撑爆。

代价是跨章一致性会变差——并行处理的各章看不到彼此。所以并行跑完后必须有一道统一校对：同一术语在各章的中英对照和定义措辞是否一致，冲突以首次定义为准。

## 六、注意力会在中段塌陷

模型对长输入的开头和结尾记得最清楚，中间部分会被系统性稀释——严重时甚至不如完全不给材料。这有几个直接后果：

- 别因为模型支持超长上下文就把整本书一次丢进去，中间章节一定会被稀释
- 每章单独处理时，把核心约束放提示开头、输出格式放结尾
- 遗漏检查要逐块做，整体回读查不出中段的遗漏
- 已知偏差：最后两三章容易被过度展开，前面几章容易偏薄。收尾时专门对齐一下各章的节点数量级

## 七、收尾去痕

分批生产会留下痕迹，交付前删掉：

- "在本章中""前面提到过""接下来会讲"这类分段生产的过渡语
- 混进来的目录、致谢、作者简介、版权页内容
- 各章节点数量级严重不均的地方
