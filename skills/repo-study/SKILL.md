# repo-study — 把陌生代码仓库读成一份自己的理解文档

## 定位

这份文档的读者只有用户一个人。成功标准是他读完能在脑子里把这个项目跑一遍，并且知道哪几处做法值得搬到自己手上，不是覆盖完整。

用户是产品经理，技术底子是知道概念但说不准。他要的不是把术语翻译成大白话——那样他跟研发对话时说不出词；也不是罗列术语——那样他看不懂。要的是保留术语原词，后面跟一句它在这个项目里用来干什么。

不限模块数，不限字数，讲清楚优先。文档长就加目录和每节摘要让它能跳读，不靠砍内容控长。

**深度是这个 skill 的主要失败点**。默认倾向是每个模块都写成中等深度的职责说明，读完只知道有哪些盒子，不知道任何一处设计精妙在哪。对抗办法是分层：用户勾选的重点维度下到机制层（读函数体，不只读签名和 docstring），其余精炼覆盖。宁可少写几个模块也要有几处真正讲透。

## 按需读取

| 文件 | 什么时候读 |
| --- | --- |
| `references/depth.md` | S3 精读前必读。怎么从「是什么」下到「机制怎么运转」，附重点维度候选清单 |
| `references/diagrams.md` | S4 画图前读。图型怎么选、画什么不画什么、语法陷阱 |
| `references/comparison.md` | 确认要做第 7 节之后再读。三档结论怎么定、最小落地动作怎么写 |
| `references/methodology.md` | 想改本 skill 的规则前读。每条约束是实测得出还是设计意图，哪些至今没验证过 |

## 流程

```
S1 侦察（不分批，建全局骨架）
  ↓
S2 用户确认（全流程唯一的停顿点）
  ↓
S3 分批精读（骨架锁定，重点维度下到机制层）
  ↓
S4 成文 + 画图 + 渲染
```

## S1 侦察

### 先探代理，再拿代码

国内直连 GitHub 经常整分钟零进展，等超时了才想起代理是浪费。先探：

```bash
for p in 7897 7890 1087 10809; do nc -z -G1 127.0.0.1 $p 2>/dev/null && echo "proxy $p"; done
```

探到就带上 `https_proxy=http://127.0.0.1:<port>` 再 clone。都探不到时看 shell 配置里有没有代理函数或别名。

```bash
git clone --filter=blob:none <url> <目标目录>
```

不用 `--depth 1`。改动热点需要完整 commit 历史，浅克隆会让这个信号直接消失。`--filter=blob:none` 保留全部历史但按需拉文件内容。

代理也不通时降级到 `npx repomix --remote <owner/repo>` 或 gitingest，并在文档头注明「无 git 历史，关键模块判断仅基于体量和调用关系」。本地目录直接用。

### 跑侦察脚本

```bash
python3 scripts/repo_survey.py <仓库路径> [--top N] [--commits N]
```

输出语言构成、源码与测试代码的体量分布、git 改动热点、文档资源、依赖与入口。

三组信号交叉才能定重点。只看体量会把生成代码当核心；只看热点会漏掉写完就不动的地基模块，比如协议定义和核心抽象基类，而那些恰恰是理解架构的入口。脚本在历史太短时会自己提示热点不可信，看到提示就以体量和入口链路为准。

### 读人写的东西

按信息质量排序：`ARCHITECTURE.md` 和 `docs/design/`、ADR、RFC 最高（作者自己讲设计意图），然后是 `README`、`CONTRIBUTING.md`、`AGENTS.md`、`CLAUDE.md`、`CHANGELOG`，最后是依赖清单（术语表的原料）。

顺手做一件事：**凡是 docstring、注释、配置文件里出现的仓内路径引用，检查它存不存在**。断链本身是信息——它通常说明作者有一套没开源的私有文档，意味着设计决策那节能看到结论但看不到论证，这个限制要写进存疑清单。

### 联网搜背景

搜背景资料，回答三个问题：这个项目为什么存在、解决什么问题、跟同类怎么比。优先级：作者本人的设计博客和演讲 > 项目官网设计文档 > HN / Reddit 深度讨论 > 二手介绍文章。

外部信源只用于背景和动机，不用来描述架构和实现。网上文章版本滞后，拿它讲实现细节比直接读代码还不准。

**搜不到是常见情况**（冷门项目、私有仓）。这时不要拿同名的无关项目硬凑，直接在文档头的信息来源里声明外部信源为零，并在存疑清单里单列一条说明没有第三方交叉验证。

### 产出全局骨架

侦察的产出是骨架不是文档：项目一句话定位、模块清单（每个一行职责，标体量和热度）、模块依赖关系、术语候选、可用文档资源、待查清单，以及下面 S2 要用的两样东西。

## S2 用户确认

全流程唯一的停顿点。给用户看侦察报告，请他定三件事。

**一，主链路。** 先判断项目形态再决定怎么问：

| 形态 | 判断依据 | 怎么处理 |
| --- | --- | --- |
| pipeline / 串行编排型 | 有总编排入口：cron 脚本、Makefile、workflow 定义 | 全链路就是主链路，分段呈现，**不要让用户四选一** |
| 请求响应型、多入口型 | 多个平级入口，彼此不串联 | 列候选链路请用户选一条 |

早期版本无条件让用户选一条，在 pipeline 项目上是错的——那些看似并列的选项其实是一条链路的几段。

**二，重点维度。** 给出候选清单请用户勾选，勾中的下到机制层，其余精炼覆盖。候选清单怎么生成见 `references/depth.md`。这是决定文档有没有用的关键判断，必须问，不要自己替他定——自动选出来的是「体量大的」，不是「他想学的」。

**三，要不要做对比章节。** 这一节不是必需的，默认不做。学一个框架本身时对比是多余的，只有用户手上有个对照物、或者正在做选型判断时才有价值。问一句「要不要跟某个项目对比」，他说要才做。

要做的话再问对比谁。有对照物就逐维度对比；没有对照物但仍想要，退化成跟同类通行做法对比。写法见 `references/comparison.md`。

不要问要不要精简模块。用户已明确不限范围。

## S3 分批精读

大仓库超上下文时按模块分批，每批带上 S1 的全局骨架。

批次之间保持一致靠一条规则：骨架在分批之前定死，每批只允许往里填充，不允许改骨架。某一批发现骨架有错，记进冲突清单继续走，不当场改——当场改会让前后批次基于不同骨架，拼出来的文档自相矛盾。

**重点维度和其余模块用两套读法**，具体见 `references/depth.md`。简单说：重点维度要打开函数体读实现，能说出这个设计的取舍点和精妙处；其余模块读签名和 docstring 即可，讲清职责和上下游。

## S4 成文 + 画图 + 渲染

按输出骨架组装，处理冲突清单。画图规则见 `references/diagrams.md`。

图写成 mermaid 代码块，每块前面加一行 `<!-- fig: 图的标题 -->`，然后跑：

```bash
python3 scripts/render_diagrams.py <文档.md>
```

它把每块渲成 SVG 存到文档同级的 `图/` 目录，并在代码块前插入图片引用。代码块保留在原处，改图时改代码重跑即可，脚本幂等。渲染失败的块会报出来，那是 mermaid 语法错，必须修——图渲不出来对读者是硬伤，不能靠自觉。

组装完自检四条：

- 第 1 节那一段，脱离全文单独读能不能懂
- 重点维度那几节，有没有说出取舍点，还是仍然停在职责描述
- 时序图上的每一步，能不能在模块拆解那节找到对应
- 存疑清单是不是空的。空的反而可疑，通常说明该标推断的地方混进正文当结论了

## 输出骨架

默认落到当前工作目录的 `<项目名>-项目理解.md`，图存到同级 `图/`。用户指定了位置就用他给的；仓库或工作区有自己的文档目录时问一句放哪，不要往某个固定路径写。

```markdown
# <项目名> — 项目理解

> 核心结论一段话。写清这个项目最值得记住的一件事，以及本文梳理出几条借鉴点、
> 几条问题，让读者知道先看哪节。
> 材料来源：代码通读范围 / 文档 / 外部信源（没有就明说没有）。基于 <commit>，<日期>。

[目录表：每节一行，一句话说清这节回答什么]

## 1 它是怎么转起来的
一段话，用一个类比讲清整体怎么运作，配一张总览图。读完这段应该能大致猜到后面各节讲什么。

## 2 全景架构
模块依赖图 + 主链路时序图 + 一段话把主链路走一遍。

## 3 模块拆解
重点维度：下到机制层，讲取舍和精妙处，带 file:line。
其余模块：职责 / 输入输出 / 上下游，一段话带过。

## 4 术语表
保留原词 + 它在这个项目里干什么用。

## 5 设计决策
为什么这么设计，每条标来源类型：代码注释 / commit / PR 讨论 / 文档 / 推断。

## 6 策略与配置（仅本地私有仓默认出）
硬编码阈值、开关、降级路径、超时重试，每条带 file:line。

## 7 对比与借鉴（可选，S2 问过要才出）
逐维度对比，三档结论 + 最小落地动作。写法见 references/comparison.md。

## 8 设计理念提纯
贯穿全局的几条主张，配一张归类图。跟第 5 节的区别：那节是单点决策，这节是可迁移的原则。

## 9 存疑清单
没验证的、没读懂的、断链的、外部信源与代码冲突的。
```

第 6 节的开关规则：本地私有仓默认出（用户在这类场景下要跟研发对话，阈值和降级逻辑是对话素材），公开仓默认不出（学一个开源框架时硬编码阈值没有学习价值）。用户点名要就出。

## 写法

### 术语

保留原词，后面跟一句它在这个项目里用来干什么。

- 只堆名词：这个模块用了 dependency injection 和 middleware chain
- 换成大白话：这个模块把零件的组装工作交给外面做
- 要的写法：用 dependency injection，模块 A 不自己 new 出 B，而是等外面把 B 塞进来。这个项目靠它在测试时把真实存储换成内存假实现，见 `core/container.py:45`

### 出处按代价分层

不均匀铺 `file:line`，按这条信息错了代价多大来定：

| 位置 | 标注要求 |
| --- | --- |
| 重点维度、具体实现、策略配置 | 必须带 `file:line` |
| 第 1 节、全景架构 | 不逐条标，整节开头声明来源（静态分析 / 代码通读 / 推断） |
| 设计决策 | 标来源类型，找不到依据就写找不到，不要编一个理由 |
| 外部信源 | 挂 `[来源名 · 日期]` |

### 复杂对比用 HTML table

markdown 表格塞不下多层内容。一个单元格里要放两三条并列要点时改用 HTML table 配 `<ul><li>`，飞书能正常渲染：

```html
<table>
  <thead><tr><th>维度</th><th>A 方案</th><th>B 方案</th></tr></thead>
  <tbody>
  <tr><td>加一个能力</td>
      <td><ul><li>动 1 处：新增一个插件包</li><li>卸载全撤销</li></ul></td>
      <td><ul><li>至少动 3 处：实现、接线、提示词片段</li></ul></td></tr>
</tbody>
</table>
```

单层内容仍然用 markdown 表格，别为了形式换。

## 第二次读同一个项目

不覆盖原文档，在末尾追加一节 `## 补充 <日期>`，并在顶部目录挂一行。

保留原判断是有意的。第一次理解可能是错的或浅的，但那个演进过程本身有价值，覆盖掉就看不到自己是怎么想明白的了。追加内容里如果推翻了之前的结论，明确写「第一次读时判断 X，实际是 Y，误判原因是 Z」。

## 红线

1. 实现细节找不到 `file:line` 依据就不写进正文，放进存疑清单。用户会拿这份文档当认知基础，编造的实现会让他一直错下去，而他不像研发那样能随手验证
2. 读不懂的代码照直写进存疑清单，注明没读懂的原因，不要用合理推测填补
3. 外部信源与代码冲突时以代码为准，并把冲突记进存疑清单，注明某文章说 X 而代码里是 Y。这种冲突往往正好标记了项目的演进节点
4. 第二次读走追加，不覆盖原文档

## 失败处理

| 情况 | 怎么办 |
| --- | --- |
| clone 慢或超时 | 先探代理再 clone，都不通降级 repomix --remote 或 gitingest，文档头注明无 git 历史 |
| 超上下文 | 按 S3 分批，不缩范围 |
| 非 git 目录 / commit 太少 | 脚本自动跳过或提示热点不可信，改用体量加入口链路定重点 |
| 外部信源搜不到 | 文档头声明为零，存疑清单单列一条，不拿同名无关项目硬凑 |
| 语言不熟（Rust、C++、Haskell 等） | 照常做，文档头声明，实现细节标置信度，存疑清单写清哪些没吃透 |
| 找不到入口 | 从依赖配置的 scripts / entry_points 找，再不行看 README 用法示例反推 |
| mermaid 渲染失败 | 必修，不是可选。多数是节点文本没加双引号，见 `references/diagrams.md` |
| npx 拉包 ECONNRESET | 渲染脚本会自己重试一次，仍失败就是代理没探到，手动带环境变量重跑 |
