# 深度分层

S3 精读前读。解决这个 skill 最容易失败的地方：每个模块都写成中等深度的职责说明，读完只知道有哪些盒子。

## 什么叫下到机制层

同一个模块，三种深度：

| 深度 | 长什么样 | 读者收获 |
| --- | --- | --- |
| 职责层 | 「clustering 模块负责把讲同一件事的内容归成一个事件」 | 知道有这个盒子 |
| 配置层 | 「用三档阈值，0.85 自动入簇，0.70 以下建新簇，中间交给 LLM 判」 | 知道盒子的参数 |
| 机制层 | 「三档的意义是把 LLM 调用压到只发生在灰区。高低两端都不花钱，成本随数据量线性增长的部分被砍到只剩中间那一小段。代价是灰区宽度直接等于成本，所以它又加了时间接近度做二次门控（`stage1_gray_max_temporal_hours: 2`），防止灰区在数据量大时膨胀」 | 知道这个设计防的是什么、代价在哪 |

多数产出停在配置层。配置层和机制层的区别不是字数，是有没有回答「为什么是这样而不是别的样子」。

再看一个来自 agent 框架的例子：

- 配置层：inbox 有 followup、steer、inject 三类输入
- 机制层：三类输入的唯一区别是一个唤醒位。`inject(input)` 就是 `send(input, 'next-step', wakeup=false)`。也就是说注入和引导在数据结构上完全相同，差别只在要不要打断模型当前的思考。把这两件事统一成一个原语的好处是，任何一个插件想往上下文里塞东西，不需要关心自己是不是在打断谁

第二种写法能让读者在遇到没见过的场景时自己推断，第一种不能。

## 重点维度候选清单

S2 请用户勾选时用。先给通用维度，再按项目类型补充专有维度。清单要具体到这个项目的实际情况，不要照抄下表的抽象名字——比如不写「容错与降级」，写「LLM 限流和失败重试怎么协调（`ai_provider_guard.py` + `enrich_items.py` 的重试队列）」。

**通用维度**（任何项目都可以问）：

| 维度 | 它回答什么 |
| --- | --- |
| 数据流 | 一条数据从进来到出去经过什么，每一步改变了它什么 |
| 状态与持久化 | 状态存在哪，怎么变更，中断了怎么恢复 |
| 扩展机制 | 加一个新能力要动几处代码 |
| 容错与降级 | 出错了怎么办，哪些错误会被吞掉 |
| 并发与调度 | 谁在什么时候跑，怎么防止互相踩 |
| 配置与开关 | 行为怎么被外部控制，哪些能热改 |
| 数据模型 | 核心实体是什么，关系怎么表达 |
| 性能关键路径 | 作者在哪里花了心思优化，说明瓶颈在哪 |

**按项目类型追加**：

- LLM / Agent 应用：prompt 怎么组装、上下文怎么裁剪、工具怎么注册和调用、记忆怎么跨会话、效果怎么评测
- Web 服务：一个请求的完整生命周期、认证与鉴权、数据访问层的抽象
- 数据管线：调度与依赖、幂等与重跑、历史数据回填
- 库 / 框架：扩展点在哪、API 的向后兼容策略、默认值的选择
- 前端应用：状态管理、渲染与数据获取的边界、路由

清单给用户时每条附上体量和文件位置，让他能判断投入产出。

## 怎么读函数体

不能全读，也不该全读。定位方法：

1. **从入口反向找**。主链路时序图上的每一步，找到对应函数，只读那个函数
2. **优先读分支多的函数**。`if` / `try` / `except` 密集的地方就是作者处理过真实问题的地方，注释也集中在那里
3. **读常量定义的上下文**。一个硬编码的数字旁边通常有注释解释它为什么是这个值，那段注释往往比函数体更有信息量
4. **读被最多地方 import 的模块**。它是这个项目的公共约定所在
5. **测试用例是策略边界的最好文档**。想知道某个函数的边界条件，看它的测试比看它的实现快

grep 能给你签名和 docstring，那只够写职责层。要写机制层必须实际打开函数体看几十行。这一步没有捷径。

## 讲透了的判据

写完一个重点维度，用这三个问题自检，答不上来说明还停在配置层：

1. **这个设计防的是什么**。任何非平凡的设计都在防某种失败。说不出防什么，说明只看到了表面
2. **代价是什么**。没有免费的设计。说不出代价，说明只抄了作者的宣传口径
3. **如果重新设计，哪里可以不一样**。能说出一个合理的替代方案并解释为什么作者没选它，才算真理解

第 3 条最难也最有价值。info2action 的两套聚类实现并存就是现成例子：v15.0 宁漏不错合，v2 实验分支宁可错合再洗。同一个团队对同一个问题给出两种相反的容错哲学，这个对比本身就把「为什么是这样」讲清楚了。

## 其余模块怎么速览

不是重点维度的模块，一段话讲清四件事就够：解决什么问题、输入输出、上下游、有没有反常之处。

反常之处值得单独留意：单文件几万行、命名与实际行为不符、一个模块被所有人依赖但没有文档。这些是下一次深挖的候选，写进文档里让用户知道存在，但这一轮不展开。

速览部分不要为了凑深度而编。写不出机制就老实写职责，把不确定的放进存疑清单。
