# repo-study 的规则是怎么来的

想改这个 skill 的规则之前先看这里。下面每一条约束都标了它是实测得出的还是设计意图，以及哪些至今没被验证过——动那些没验证的部分不需要有心理负担，动实测得出的那些要先想清楚为什么当时的结论不再成立。

首次实测对象 [info2action](https://github.com/yike-gunshi/info2action)，18.5 万行，Python + TypeScript。

### 对照参照文档补的三处结构性缺失

参照一份手写的深度架构拆解文档（1042 行 / 21 张图）。差距不在长度，在结构：

1. **深度分层**。原版每个模块均匀中等深度，读完只知道有哪些盒子。新增 `references/depth.md`，区分职责层 / 配置层 / 机制层，给出重点维度候选清单、读函数体的定位方法、三条讲透判据。S2 增加勾选环节，用户勾中的下到机制层，其余精炼覆盖
2. **图密度**。原版 2 张对参照的 21 张。新增 `references/diagrams.md`，八种图型的选用场景、边要标注关系类型、subgraph 标题要说清这层解决什么问题
3. **对比章节**。原版第 7 节「值得学什么」是泛泛观察。新增 `references/comparison.md` 和输出骨架第 7 节：三档结论（值得借鉴 / 合理不必改 / 设计问题）、最小落地动作要写成能直接对研发说的话、结论前置

另外补了：文档开头 callout 给数量化结论、复杂对比用 HTML table 配 ul、新增第 8 节设计理念提纯。

输出骨架从 8 节改为 9 节，原「值得学什么」被「对比与借鉴」吸收。

### 本轮删减

按 skill-build 的每轮必删原则：删掉「默认只画两张，多了会稀释注意力」整段（实测证伪），删掉主链路无条件四选一的强制性，失败处理表从 7 行合并为 8 行但每行信息量提高。

| --- | --- | --- |
| 行数 / 字符 | 477 / 20,836 | 672 / 25,622 |
| Mermaid 图 | 2 | 9，全部渲染成 SVG 并插入引用 |
| `file:line` 引用 | 78 | 53 |
| 对比章节 | 无 | 有，跟一个对照项目逐维度比，3 条借鉴 + 1 条合理不必改 |
| 深度 | 停在配置层（列出阈值是多少） | 到机制层（三条灰区放行规则的补偿阶梯、close_time 是公共必要条件、召回取三档最小值的用意） |

`file:line` 从 78 降到 53 是预期内的：旧版把出处均匀铺在每个模块上，新版按代价分层，只在重点维度和具体实现上密集标注。密度不是质量指标。

### 已验证

- **深度分层有效**。第 3.1 节写出了代码注释里没有的两件事：`close_time` 是三条放行规则的公共必要条件，以及信号越弱要求实体重合数越多的补偿阶梯。这是打开函数体读 `pipeline.py:1140-1145` 才能得到的，grep 签名拿不到
- **图密度上去没有变成为画而画**。9 张图各自承担不同结构，没有出现两张图讲同一件事
- **渲染脚本在真实文档上跑通**，9/9 成功，代理自动命中，引用位置正确
- **对比章节写得出实质结论**。抓到一条强证据：对照项目的评测文档里挂着一条上线前必须人工确认的前提，正好是 info2action 的 PROMPT_VERSION 机制能消除的那类问题

### 仍未验证

- **对比章节的退化模式**（没有对照物时跟同类通行做法比）。这一轮有现成的对照项目，退化路径没走到
- **S3 分批的骨架锁定**。两轮上下文都没超限，这条机制从未真正触发
- **第 7 节的三条借鉴能不能真的落地**。写成了给研发提需求的话术，但没有实际拿去提过

### 本轮暴露的新问题（已修）

**P8 · 对比维度的选择缺少约束**。这次选了 4 个维度，其中一个的对照侧依据只有 grep 加一份架构文档，只能标推断。原文没说清材料不足时该降级标推断还是干脆不比。

改法：`references/comparison.md` 的三档结论那节把证据不足拆成两种处理——一侧只差个别细节的可以标推断硬着头皮比，一侧材料根本不够支撑结论的直接不比并在节末声明。判据是「如果推断错了，这条结论会不会反过来」，会反过来就不该比。挂个推断标签硬比看起来覆盖更全，实际是给读者一个不能用的结论。

**P9 · 反向对比没有写进 references**。这次自发写了一节反向对比（info2action 缺什么、对照项目强在哪），能防止整节变成单向夸赞，但规则里没有这一条。

改法：并进「常见写坏的方式」的写成夸赞那条，作为对抗手段。同时说明它的附加价值——反向那节通常能解释为什么借鉴点集中在那几个维度（对照物的短板正好落在这个项目的长板上）。附一条约束：找不到短板就说没找到，不为了平衡硬凑。

## 第 2 轮 · 发布前的通用化改造

准备开源前做的三处调整，都不是因为发现了缺陷，是原设计跟单一使用者的习惯绑得太死：

1. **对比章节从必做改为可选**。原设计把它当成固定的第 7 节，但纯粹想搞懂一个框架怎么运作时，对比是多余的负担。改成 S2 明确问一句要不要做，默认不做；要做才继续问对比谁
2. **落盘路径去掉硬编码**。原来写死落到一个特定的知识库目录，换个人用就会往不存在的路径写。改成默认落当前工作目录，用户指定了就听用户的，仓库自带文档目录时问一句
3. **代理探测的说明去个人化**。原来点名从某个 shell 配置文件里找代理函数，改成通用表述

同时对本文件做了脱敏：移除对照项目的产品名、内部文档名与具体结论原文，只保留方法论层面的描述。
